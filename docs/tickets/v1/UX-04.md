## Actor
Student, Teacher (every list and home surface they see). Quality/Admin lists are out of scope.

## Problem
The API serializes every status as an integer and no DTO carries a status name. The generic dashboard
(`features/dashboards/pages/dashboard-page.component.*`) renders `row['statusName'] || row['status']`, so
badges show `0`, `1`, `2`; card titles fall back to an id or email; the field list shows "Currency",
"Updated", "Total", "Count"; every section has a search box and a Refresh button
([UX_PRINCIPLES §6.1, §6.6](../../product/UX_PRINCIPLES.md#66-technical-or-inappropriate-wording-found)).
Notifications (`GET /notifications`) carry **English-only** server titles and bodies (e.g.
"Complete payment to keep your Offer", `OpenMarketplaceService.cs:347`), shown unchanged in Arabic.
Checkout shows raw id fragments as "Order"/"Request" references (`payment-page.component.html:55-57`).
The dedicated screens (request, offers, opportunity, order, session, application review) already map
statuses through `Demand.statusKey/statusTone`, `orderStatusKey`, `Session.statusKey/statusTone`,
`Review.statusTone` — but the Arabic terms drift from the Product Contract (below).

## User goal
As a student or teacher, I want every item to tell me in plain words what state it is in and what I
should do, so that I never have to decode numbers, ids or database field names.

## Business rule
- [UX_PRINCIPLES §2 rule 4](../../product/UX_PRINCIPLES.md#2-rules): product words, never code words.
- [Contract §3](../../product/TAFSEEL_PRODUCT_CONTRACT.md#3-terminology) product terms are authoritative
  where the contract defines them (request and order statuses); this ticket supplies the terms the contract
  does not list, as presentation copy only.
- The server decides which actions are allowed; the "user action" column is the CTA label shown when the
  item's own screen offers that action. No backend enum changes.

## Business states
All mappings below. Tones use the existing `tf-badge[data-tone]` tokens: `neutral`, `info`, `warning`,
`success`, `danger`. **Rule of tone:** `warning` = waiting for *this viewer*; `info` = in progress / waiting for
someone else; `success` = done well; `danger` = ended without the intended outcome; `neutral` = inactive/historical.

## Preconditions
None (presentation over existing responses).

## Happy path
1. Any Student/Teacher list or home loads its existing endpoint.
2. Each item is presented through one shared mapping (`status → { labelKey, tone, actionKey }`, role-aware).
3. The user reads a product status, the item's key fields and at most one CTA.

## Negative cases
| Case | What the user sees |
|------|--------------------|
| Unknown/new enum value | «غير معروف» / "Unknown" (neutral) — never the number; a console warning in development |
| Missing title | fallback chain above |
| Missing other-party name | «المعلم» / "Teacher" or «الطالب» / "Student" |
| Unknown notification type | «لديك تحديث جديد» / "You have a new update" |
| Null amount/date | field omitted (never "null", "—" only inside tables) |

## Authorization
Unchanged. The mapping only renders data the viewer already receives; role-aware labels use the viewer's
id vs `studentId`/`teacherId` from the same response.

## UX
- **Entry point:** every Student/Teacher list: Student Overview, My learning (Requests, Orders), Sessions,
  Saved teachers, Reviews & disputes, Notifications; Teacher Home, Work (Requests, Orders, Sessions),
  Opportunities, Qualifications, Earnings/Withdrawals lists; `/messages`; `/disputes`; checkout summary;
  offers and opportunity screens (align terms).
- **Information hierarchy:** title → status badge → secondary line → ≤ 2 fields → one CTA.
- **Primary CTA per state:** the CTA columns above; only one per card; items with no viewer action show a
  quiet «افتح» / "Open" link.
- **Wording (AR / EN):** tables above. Locale keys to change to the Contract terms:
  `demand_status_clarification` «سؤال من المعلم» → «المعلم لديه سؤال»; `demand_status_open` «مفتوح للعروض» →
  «يستقبل العروض»; `demand_status_reserved` → «العرض محجوز للدفع»; `demand_status_converted` «تحوّل إلى طلب شراء» →
  «أصبح طلب عمل»; `order_status_payment_required` «مطلوب الدفع» → «بانتظار الدفع»; `order_status_payment_confirmed`
  «تم تأكيد الدفع» → «تم الدفع»; English `demand_status_clarification` → "Teacher asked a question",
  `demand_status_open` → "Receiving offers".
- **Mobile (390px):** badges wrap under the title when the title exceeds one line; no truncated status; cards
  full width; CTA ≥ 44px.
- **Loading / empty / error / not-available states:** unchanged per list (owned by `UX-01`/`UX-02`/`UX-03`
  screens); this ticket guarantees no raw value appears in any of them.
- **Confirmation dialogs:** none.
- **Gate question:** yes — every value a student or teacher can see has an everyday Arabic and English term
  and, where they must act, a verb CTA.
