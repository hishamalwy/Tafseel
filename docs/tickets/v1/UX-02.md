## Actor
Teacher (signed in, role Teacher) — from first sign-in after applying to a published teacher with work.

## Problem
Teacher Home (`/teacher/home`) is the generic dashboard over `/teachers/me/business/home-summary`,
`/withdrawals/balances` and `/notifications?pageSize=100` (`features/dashboards/models/dashboard.ts:50`):
- counters as raw fields;
- balances as a raw object;
- up to 100 notifications as identical cards;
- no publication blocker and no ordering by what the teacher must do
  ([UX_PRINCIPLES §6.3](../../product/UX_PRINCIPLES.md#63-teacher)).

An unpublished teacher is not told the one thing preventing students from finding them. A published teacher
with a paid order to start sees the same grid as one with nothing to do.

## User goal
As a teacher, I want my home to show first what stops students from finding me (until I am visible), then what
needs my action, then open requests I could win, my next session and what I have earned — so that I can run my
teaching from one screen.

## Business rule
No new rule. Presentation of existing states:
- Contract §3.15 and §4.4: readiness and publication are decided by the server
  (`GET /teachers/onboarding-status` → `blockingReasons`, `status`); the UI explains them.
- §3.3: the teacher reviews a waiting Direct Request (accept with price/delivery/revisions, ask, decline);
  a student's reply returns the request to *Waiting for the teacher*.
- §3.6: the teacher starts a paid order, delivers while *In progress* or *Revision requested*.
- §3.8: after the end the teacher asks to complete, or reports a student no-show after 15 min grace, and
  confirms/contests a student's teacher-no-show report; reschedules proposed by the student are answered.
- §3.4: only qualified teachers with a matching active offering see Open Requests.
- §3.9 / `FIN-01`: Available, Clearing, next availability date.

## Business states

`blockingReasons`, excluding `profile_not_published`, is the blocker card. When the only remaining reason is
`profile_not_published` (`readyForPublication = true`), the "ready" card is shown.

Supporting line:

- T2 «قبل {outcomeReviewDeadline}» (omitted when null);

Not action (waiting for others) — not on the home; reachable in Work:
- request `1 ClarificationRequested` (waiting for the student);
- order `0 + Pending`;
- order `1 InProgress` not overdue;
- order `2 Delivered`;
- sessions `6`/`7` pending the student;
- a reschedule the teacher proposed.

The footer link «عرض كل أعمالي» / "See all my work" → `/teacher/work` always shows.

**Card priority rules**
1. Sort by row number (T1 first), then earliest deadline (`startsAt`, `outcomeReviewDeadline`, `agreedDeliveryAt`), then oldest `createdAt` for requests (first come, first served).
2. At most 3 action cards, then «عرض كل ما يحتاج إجراء ({n})» → `/teacher/work?view=action` (`UX-03`).
3. Setup card (if any) is always above everything and is the only filled button on screen.

### Open-request opportunities preview (published teacher only)
The first 3 of `GET /open-marketplace/opportunities` (ordered by deadline) where `myOffer` is null. Card: request title,
«{service} · {subject}», «آخر موعد {deadline}», «الميزانية {min}–{max}» or «ميزانية مرنة»; CTA «اعرض الطلب» /
"View request" → `/teacher/opportunities/:id`. Header «طلبات مفتوحة تناسبك» / "Open requests for you" + «عرض الكل ({totalCount})» /
"See all ({totalCount})" → `/teacher/opportunities`. Empty: «لا توجد طلبات مفتوحة تناسب خدماتك الآن.» / "No open requests
match your services right now." (no CTA).

### Upcoming live session
Nearest `1 Confirmed` session with `startsAt` > now + 15 min: student name, service, «{weekday} {date} · {time}», «تبدأ بعد
{relative}»; CTA «تفاصيل الجلسة» → `/live-sessions/:id`. Hidden when none.

### Earnings summary (from `FIN-01`)
Heading «أرباحي» / "Earnings"; three compact lines: «متاح للسحب {available}», «قيد الإتاحة {pendingClearance}», and
«أقرب مبلغ يصبح متاحًا في {date}» (or «يصبح متاحًا قريبًا» / omitted per FIN-01 rules); link «تفاصيل الأرباح» / "Earnings
details" → `/teacher/earnings`. Zero/empty: «لا توجد أرباح بعد» / "No earnings yet". "Being transferred" is shown only on FIN-01.

## Happy path
**Unpublished new teacher**
1. Approved teacher signs in → `/teacher/home`.
2. `onboarding-status` returns `blockingReasons = [profile_incomplete, active_service_required, profile_not_published]`.
3. Home shows «أكمل ملفك الشخصي» with «أكمل الملف» and «خطوات متبقية: 2»; nothing else (no work, no opportunities, no earnings).
4. After saving the profile the teacher returns; the card becomes «فعّل خدمة واحدة على الأقل».

**Published teacher**
1. Home loads onboarding status; `status = Published`.
2. Parallel loads: assigned requests (status 0), assigned orders, sessions, opportunities, balances.
3. Teacher sees T6 «تم الدفع — ابدأ العمل» above T8 «طلب جديد من …», then three opportunities, next session, earnings.
4. Taps «ابدأ العمل» → order detail (start is confirmed there).

## Negative cases
| Case | What the teacher sees |
|------|------------------------|
| `onboarding-status` fails | Error state with retry (the home cannot decide the view without it) |
| Teacher in application stage (`qualification_required`) | Setup card only; no other calls are made |
| Unpublished teacher who already has work or earnings (e.g. went invisible, or suspended later) | Setup card first, then Action required, Upcoming session and Earnings; the opportunities preview is hidden until visible. *(Refines UX_PRINCIPLES §4 "replaces everything below": paid work must never be hidden.)* |
| Any secondary call fails | Its section shows «تعذّر التحميل» / "Couldn't load" + «إعادة المحاولة» inline; other sections render |
| Opportunities returns 0 / all have `myOffer` | Empty preview line |
| `account_suspended` | Suspended card; action and earnings still visible if present (read-only screens decide actions) |
| 401 / wrong role | Session handling / existing `teacher/:section` guard |

## Authorization
- `GET /teachers/onboarding-status`: policy `TeachersApply` (teacher role); own status only.
- `/learning-requests/assigned`, `/orders/assigned`, `/open-marketplace/opportunities`: role Teacher, own
  assignments and eligible opportunities only (opportunities contain no private student data — 3B proven).
- `/live-sessions/mine`: participant only. `/withdrawals/balances`: `WithdrawalsRequest`, own balances.
- The home never shows student contact details, other teachers' offers, internal ledger or maturity terms.

## UX
- **Entry point:** after sign-in for teachers (`AppRoutes.TeacherHome` `/teacher/home`); Teacher navigation item 1
  «الرئيسية» / "Home" (`UX-03`); onboarding `NextUrl` for published teachers.
- **Information hierarchy:**
  - **Unpublished:**
    1. greeting;
    2. setup card with steps left;
    3. (only if present) Action required, Upcoming session, Earnings.
  - **Published:**
    1. greeting «أهلًا {firstName}»;
    2. Action required «يحتاج انتباهك» (≤ 3);
    3. Open requests for you (≤ 3);
    4. Your next session;
    5. Earnings.
- **Primary CTA per state:**
  - setup card CTA when unpublished;
  - otherwise the first action card's CTA;
  - with no action cards: no filled button (the opportunities "View request" buttons are outline);
  - error: «إعادة المحاولة».
- **Wording (AR / EN):** tables above; extra keys:
  - `th_nothing_needed` «لا يوجد ما يحتاج انتباهك الآن.» / "Nothing needs your attention right now.";
  - `th_error` «تعذّر تحميل صفحتك الرئيسية.» / "We couldn't load your home.";
  - `th_section_error` «تعذّر التحميل.» / "Couldn't load.".

  Never shown: "ledger", "maturity", "escrow", "publication" as an English word, "Onboarding", blocker codes,
  counts labelled "Count", ids, search, Refresh. Services are called «خدماتي» with the Tafseel-catalog explanation
  (see `UX-03`).
- **Mobile (390px):**
  - single column; setup card full width with the CTA ≥ 44px;
  - opportunities preview as stacked cards (no horizontal carousel);
  - earnings as three lines, not a table;
  - above the fold: greeting + setup card (unpublished), or greeting + up to 3 action cards (published);
  - no horizontal scroll.
- **Loading / empty / error / not-available states:**
  - loading: a skeleton setup-or-action card until onboarding status resolves, then per-section skeletons;
  - published with nothing to do: `th_nothing_needed`, then the other sections;
  - error: `th_error` + retry;
  - section error: inline.
- **Confirmation dialogs:** none on the home (start, deliver, confirm and publish are confirmed on their screens).
- **Gate question:** yes — the teacher sees one sentence about what stops students finding them, or what to do next,
  with a verb button; money is described in FIN-01's plain words.

## API contracts
No new API contract; presentation/composition only.

| UI action | Endpoint | Verb | Request | Headers / concurrency | Response | Resulting server state |
|-----------|----------|------|---------|-----------------------|----------|------------------------|

| Action: waiting requests | `/api/v1/learning-requests/assigned?status=0&page=1&pageSize=50` | GET | — | Bearer | `PagedResult<LearningRequestDto>` (`clarifications[].senderId`, `studentDisplayName`, `serviceNameArabic/English`, `createdAt`) | none |
| Action: orders | `/api/v1/orders/assigned?page=1&pageSize=50` | GET | — | Bearer | `PagedResult<OrderDto>` (`status, paymentStatus, isOverdue, agreedDeliveryAt, teacherNet, requestTitle`) | none |
| Action + upcoming session | `/api/v1/live-sessions/mine?page=1&pageSize=50` | GET | — | Bearer | `PagedResult<LiveSessionDto>` | none |
| Opportunities preview | `/api/v1/open-marketplace/opportunities?page=1&pageSize=20` | GET | — | Bearer | `PagedResult<OpenRequestDto>` (`myOffer`, `deadline`, `budgetMin/Max`, `serviceName(Arabic)`, `subjectName(Arabic)`, `totalCount`) | none |
| Earnings summary | `/api/v1/withdrawals/balances` | GET | — | Bearer | `BalanceDto[]` | none |

`GET /teachers/me/business/home-summary` (counts) is not needed by the home; `UX-03` may use `unreadMessages` and
`directRequests` for navigation badges. **Endpoint audit conclusion:** existing reads are sufficient; the teacher
home makes one call for an applying teacher and six parallel reads for a published one — no demonstrated performance
or correctness problem, so no aggregation endpoint. Assigned requests are filtered server-side by `status=0`; orders
older than the newest 50 in an actionable state are reachable from Work.

Error codes the UI must explain: none new.
