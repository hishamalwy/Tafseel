## Actor
Student writing a Direct Request.

## Problem
The Direct Request wizard always shows «ساعدني في الكتابة» / "Help me write this"
(`new-request-page.component.html:100-102`). Pressing it calls `POST /api/v1/ai/request-assistant`
(`http-request.gateway.ts:59`). With `Ai:Enabled = false` (the default in `appsettings.json:83-90` and outside
Development) or without `GROQ_API_KEY`, the provider returns `Disabled`/`MissingCredentials` (`GroqAiProvider.cs:24,50-53`).
The assistant then answers "unavailable" and the page shows «المساعد غير متاح حاليًا.»
(`new-request-page.component.ts:286-291`). This is a dead control ([UX_PRINCIPLES §6.6](../../product/UX_PRINCIPLES.md#66-technical-or-inappropriate-wording-found),
PRODUCTION_READINESS U10).

The client has no way to know the AI state before clicking. No capability endpoint exists; the only similar
pattern is `GET /api/v1/payments/mock/capabilities` (`MockPaymentSimulatorController.cs:20-22`,
`PaymentCapabilitiesDto`).

## User goal
As a student, I want to see the writing helper only when it actually works, so that I don't press a button that
does nothing.

## Business rule
- The student AI brief assistant is **LATER** (`V1_SCOPE` row J3-04; `B11-11`): `Ai.Enabled` is off in Production
  until the provider and safety review are decided. It must be hidden while disabled.
- The AI backend (`AiMarketplaceController`, assistant, provider) is **not removed**.
- Enabled means: `Ai:Enabled = true` **and** provider credentials present (the provider can actually be called).
  This is the existing runtime condition, exposed read-only. No new rule.

## Business states
| Server configuration | `requestAssistant` | Wizard |
|----------------------|--------------------|--------|
| `Ai:Enabled = false` | `false` | Helper button, draft panel and helper toasts not rendered |
| `Ai:Enabled = true`, no `GROQ_API_KEY` | `false` | Hidden |
| `Ai:Enabled = true`, key present | `true` | Button shown; existing behaviour (draft, use, discard; transient "busy/timeout" toast) |
| Capability call fails or is slow | treated as `false` | Hidden (fail closed); never shown then removed while typing |

## Preconditions
Signed-in student on `/requests/new` (direct wizard).

## Happy path
**Disabled (Production V1)**
1. Student opens the direct request wizard.
2. The page reads `GET /api/v1/ai/capabilities` → `{ requestAssistant: false }`.
3. The goal step shows the text area only; no helper button.

**Enabled (Development / a future environment)**
1. Same call → `{ requestAssistant: true }`.
2. «ساعدني في الكتابة» appears next to the goal field; pressing it works as today.

## Negative cases
| Case | What the student sees |
|------|------------------------|
| Capabilities 401/403/5xx/timeout (2 s budget) | No helper button |
| Enabled, but the provider is rate-limited or times out at use | Existing toast «المساعد غير متاح حاليًا.» (transient) — the button stays |
| Configuration changes while the page is open | Takes effect on next page load |
| Student has no title/goal yet | Existing «أضف عنوانًا أو هدفًا أولًا.» |

## Authorization
- `GET /api/v1/ai/capabilities`: same policy as the assistant, `StudentsCreateRequests` (the only UI consumer is the
  student wizard). Non-students: 403 (the UI treats it as hidden).
- **Not** counted against the `ai` rate-limit partition (10/min per user): the action is excluded from
  `[EnableRateLimiting("ai")]` (`[DisableRateLimiting]` or a separate controller).
- Response reveals only two booleans' conjunction; never the provider, model, endpoint or key presence separately.

## UX
- **Entry point:** `/requests/new` direct request wizard, goal step.
- **Information hierarchy:** unchanged when enabled; when disabled the goal field is the only element.
- **Primary CTA per state:** «التالي» / "Next" (unchanged). The helper is a secondary inline action.
- **Wording (AR / EN):** no new copy; existing `req_ai_help` «ساعدني في الكتابة» / "Help me write this",
  `req_ai_draft`, `req_ai_use`, `req_ai_discard`, `req_ai_failed`.
- **Mobile (390px):** no reserved space or gap when hidden.
- **Loading / empty / error / not-available states:** while the capability loads the button is not rendered (no
  placeholder); error = hidden.
- **Confirmation dialogs:** none.
- **Gate question:** yes — the student only sees a helper that works.

## API contracts
**New read contract (1 endpoint).** Justification: the UI cannot learn the AI state before use, and the alternatives are
worse. Probing `POST /ai/request-assistant` spends rate-limit budget, sends user text and shows-then-hides the button.
A build-time client flag drifts from server configuration. This is not an aggregation endpoint; it mirrors the existing
`payments/mock/capabilities` pattern.

| UI action | Endpoint | Verb | Request | Headers / concurrency | Response | Resulting server state |
|-----------|----------|------|---------|-----------------------|----------|------------------------|
| Wizard loads | `/api/v1/ai/capabilities` | GET | — | Bearer; policy `StudentsCreateRequests`; excluded from `ai` rate limit; `Cache-Control: no-store` (global `/api`) | `200 AiCapabilitiesDto { "requestAssistant": boolean }` | none |
| Press "Help me write this" (enabled only) | `/api/v1/ai/request-assistant` | POST | `{ notes }` (unchanged) | Bearer; `ai` rate limit (unchanged) | `AiRequestAssistantResult` (unchanged) | none |

Server definition: `requestAssistant = AiOptions.Enabled && provider credentials configured` — the same condition
`GroqAiProvider` uses to create its client. Contract inventory: add the route to the API contract list so
`check-api-contract --strict` stays at 0 violations (server route + client call + DTO).

Error codes the UI must explain: none (all failures → hidden).

## Analytics / observability
None new (existing AI provider logging records `Disabled`/`MissingCredentials` only when the assistant is called, which
no longer happens while disabled).

## Acceptance criteria
- [x] AC1 With `Ai:Enabled=false` the capability returns `requestAssistant:false` and the wizard renders no helper button, draft panel or AI toast.
- [x] AC2 With `Ai:Enabled=true` and no key → `false`; with a key → `true` and the button works as today.
- [x] AC3 Capability failure hides the button.
- [x] AC4 Capability reads do not consume the `ai` rate-limit budget.
- [x] AC5 Non-student → 403; response contains no provider/model/key information.
- [x] AC6 Strict contract gate 0 violations with the new route; AI backend endpoints unchanged.

## Out of scope
- Enabling AI in any environment, provider choice, safety review (`B11-11`).
- Discovery and product-help AI endpoints (no V1 UI uses them).
- Admin AI tools.

## Dependencies
None.

## Evidence (filled at Done)

**Done 2026-09-17** — [UX-07/UX-08 audit](../../audits/ux07-ux08-2026-09-17/README.md).

Built: `GET /api/v1/ai/capabilities` → `AiCapabilitiesDto { requestAssistant }`, policy
`StudentsCreateRequests`, `[DisableRateLimiting]` so a capability read never spends the `ai` budget.
`requestAssistant` is `IAiProvider.IsAvailable`, which for `GroqAiProvider` is exactly the condition its
constructor already applies (enabled **and** credentials present). Client:
`AssistWithBrief.isAvailable()` reads it once per application load and caches it, and the wizard renders the
helper button and draft panel only when it is true — a refusal, outage or timeout resolves to false.

Tests: `GroqAiProviderContractTests` (4 cases: enabled × credentials → available), `Release9AiAssistedMarketplaceTests`
(capability true/false, no provider/model/key in the body, anonymous 401 and teacher 403, and 12 reads
followed by a working assistant call proving the reads are not rate-limited),
`http-request.gateway.spec.ts` (2 cases: mapping, and anything but an explicit yes is no) and
`new-request-page.component.spec.ts` (5 cases: visible when enabled, absent when disabled, absent on failure
with the page still usable, asked once, Arabic wizard intact). Browser journey steps 4–6: with the host's
default configuration the Arabic wizard at 390px shows no helper, no draft panel and no "unavailable"
message, the only AI request made is one capability read, and a teacher is refused.

The endpoint snapshot `tests/contracts/api-endpoints.json` carries the new route; the strict contract gate
is 214/214 with 0 violations. No AI endpoint's authorization changed and no rate limit was weakened.
