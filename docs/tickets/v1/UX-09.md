## Actor
Student paying for an accepted Direct Request; Teacher (sees the same prices on their side of the request and order).

## Problem
DEC-02 lets a teacher accept a Direct Request at an agreed price different from the listed Teacher Offering price.
The student must see this before paying. Today they cannot:
- **Checkout mislabels the agreed price.** It shows the order price under «السعر المدرج» / "Listed price"
  (`payment-page.component.html:48-50`, key `pay_context_price`; the line is `order.price`, `payable.ts:78`).
- **No comparison anywhere.** The order detail shows only "Price" and "Total" (`order-detail-page.component.html:133-134`).
  The request detail shows only the budget (`request-detail-page.component.html:118`).
- **The listed price is lost at creation.**
  - Teacher Offering prices are updated in place (`MarketplaceService.UpdateServiceAsync` → `TeacherService.Configure`,
    `Marketplace.cs:197-210`).
  - `OrderService.CreateRequestAsync` validates the offering's price and currency (`OrderService.cs:52-53`) but does not
    store them.
  - `LearningRequest` has only budget fields (`Orders.cs:106-108`), and `Order.Price` is the agreed price.

## User goal
As a student, I want to understand whether the teacher's price after reviewing my request differs from the price I saw
when I sent it, and what I will pay in total, before I decide to pay.

## Business rule
- **DEC-13 (decided 2026-09-15, Option A)** — [Contract §3.2/§3.3](../../product/TAFSEEL_PRODUCT_CONTRACT.md#32-teacher-offering):
  - **Snapshot at creation.** For a Direct Request, Tafseel preserves the Teacher Offering price the student actually saw when
    the request was created, as an **immutable historical snapshot**.
  - **Later edits don't change it.** Edits to the Teacher Offering never change or reinterpret that price.
  - **Server-captured.** The server captures it when the request is created, from the offering the student selected. A price
    sent by the client is never authoritative.
  - **Mandatory for new requests.** Every new Direct Request has a snapshot.
  - **No backfill.** Direct Requests created before the snapshot existed keep **no** snapshot. They are never backfilled
    (least of all from the current offering price), and no listed-vs-agreed comparison is shown for them.
  - **Open Requests are unaffected.** Their price comes from the chosen Teacher Offer.
- **DEC-02 unchanged:**
  - the agreed price may differ from the snapshot (higher or lower) but must stay inside the Admin Catalog Service policy;
  - the budget is guidance;
  - the student accepts the agreed amount **only by proceeding to payment**.
- **Fees unchanged.** Order fee and total are computed from the agreed price, with the snapshotted fee percentages
  (Contract §3.7). Financial semantics are otherwise unchanged.

## Business states
| Direct order before payment | Listed snapshot | Shown to the student |
|-----------------------------|-----------------|----------------------|
| snapshot present, same currency as the order, `listed ≠ agreed` | e.g. 100 SAR vs 150 SAR | **Comparison:** price when sent · price after review · fee · total to pay |
| snapshot present, `listed = agreed` | 100 vs 100 | **No comparison:** price · fee · total to pay |
| snapshot null (historical request) | — | **No comparison:** price · fee · total to pay (never a fabricated listed price) |
| snapshot currency ≠ order currency (not possible in V1: SAR only, acceptance enforces offering currency) | — | No comparison |
| Order paid / in progress / completed | as above | Order detail keeps the same rows; labels «الإجمالي» / "Total" instead of "Total to pay" |
| Open-request order | always null | No comparison (unchanged) |

Snapshot lifecycle: *absent* → captured once at Direct Request creation → never changes (no domain method can alter it;
Teacher Offering edits and request acceptance leave it untouched).

## Happy path
1. The teacher's «شرح مسجّل» Teacher Offering is 100 SAR.
2. The student sends a Direct Request for it. The server reads that offering and stores `ListedPriceAtRequest = 100`,
   `ListedCurrencyAtRequest = SAR`.
3. The teacher edits the offering to 120 SAR.
4. The teacher accepts the request at 150 SAR (inside policy). The order snapshot is price 150, fee 8% = 12, total 162.
5. The student opens the request detail. The accepted request shows the price panel: 100 when sent · 150 after review ·
   fee 12 · total 162, and «ادفع الآن».
6. The order detail and the checkout show the same four rows with the same labels.
7. The teacher edits the offering again (e.g. 130 SAR). All three surfaces still show 100 as the price when the request
   was sent.
8. The student pays; the payment amount is 162.

## Negative cases
| Case | Behaviour |
|------|-----------|
| Client posts `listedPriceAtRequest` (or any price) in `POST /learning-requests` | Ignored: `CreateLearningRequest` has no such member; the server value comes from the offering |
| Offering inactive, superseded, not eligible, or outside policy at creation | Existing `teacher_service_not_found` / policy refusal — no request, no snapshot |
| A second capture of the snapshot | Domain refuses (`listed_price_immutable`), mirroring `service_identity_immutable` |
| Capture attempted on an Open Request | Domain refuses (`invalid_request_transition` or dedicated code) — Open Requests never carry it |
| Historical Direct Request (snapshot null) is accepted and paid | Works as today; no comparison anywhere |
| Student does not want the agreed price | Existing actions before payment: «راسل المعلم» / "Message the teacher", «إلغاء الطلب» / "Cancel the order"; nothing charged |
| Another student / an unassigned teacher reads the request or order | 404 (existing participant rules); lists never include it |
| Agreed price outside policy | Refused at acceptance (`service_price_out_of_policy`) — never reaches the student |

## Authorization
- `POST /learning-requests`: role Student (unchanged). The snapshot is server-side only.
- `GET /learning-requests/{id}` and `/mine`/`/assigned`, `GET /orders/{id}` and `/mine`/`/assigned`: participants only
  (unchanged). Other users get 404 by id and never see the row in lists.
- The teacher of the request sees the same snapshot (it is their own offering price at that time). No new data is exposed to
  anyone else; no Admin surface changes.

## UX
- **Entry point:**
  - Direct Request detail `/requests/:id` after acceptance (next-step panel; the page already loads the student's orders to
    find the resulting order);
  - order detail `/orders/:id` before payment;
  - checkout `/checkout?orderId=`;
  - reached from Student home card A5 (`UX-01`) and the "PaymentRequired" notification.
- **Information hierarchy (one shared price panel, identical on all three surfaces):**
  - With comparison:
    1. «السعر عند إرسال الطلب» / "Price when you sent the request" — {listed} (secondary weight).
    2. «السعر بعد مراجعة المعلم لطلبك» / "Price after the teacher reviewed your request" — {agreed} (emphasis).
    3. «رسوم خدمة تفصيل ({percent}٪)» / "Tafseel service fee ({percent}%)" — {studentFeeAmount}.
    4. «الإجمالي المطلوب» / "Total to pay" — {studentTotal} (largest).
    5. Note «لن يُخصم أي مبلغ إلا إذا اخترت الدفع.» / "Nothing is charged unless you choose to pay."
  - Without comparison:
    1. «السعر» / "Price" — {agreed}.
    2. Fee.
    3. «الإجمالي المطلوب» / "Total to pay".
    4. The same note.
- **Primary CTA per state:** before payment «ادفع الآن» / "Pay now" (request detail → checkout; order detail → checkout;
  checkout → pay). After payment, none (the panel stays on the order detail with «الإجمالي» / "Total").
- **Wording (AR / EN):**
  - labels above;
  - `pay_context_price` («السعر المدرج» / "Listed price") is no longer used for the agreed price; the checkout, order detail
    and request detail use only the panel labels, so **no contradictory price labels**;
  - forbidden in both languages: «زيادة السعر» / "price increase", «المعلم غيّر سعرك» / "teacher changed your price",
    "snapshot", "version", "listed price at request", «السعر المدرج».
- **Mobile (390px):**
  - label/amount rows with amounts aligned to the end; labels wrap to two lines; no truncation;
  - checkout sticky bar: «الإجمالي المطلوب {studentTotal}» + «ادفع الآن», with the panel above in the scrolling receipt;
  - no horizontal scroll;
  - touch targets ≥ 44px.
- **Loading / empty / error / not-available states:** inherited from each screen. While the order is loading, the request
  detail shows no panel (no partial price). The fee row always uses the order's `studentFeePercent`, never a constant.
- **Confirmation dialogs:** none new. Pressing pay on checkout — the sticky bar shows the total — is the explicit acceptance.
- **Gate question:** yes — two plain labels say when each price applied, the total is explicit, and the note says nothing
  happens unless the student pays; the wording is neutral whether the price went up or down.

## API contracts
Existing endpoints; **two nullable read fields added** to two existing DTOs. No new endpoint, no request change.

| UI action | Endpoint | Verb | Request | Headers / concurrency | Response | Resulting server state |
|-----------|----------|------|---------|-----------------------|----------|------------------------|
| Student sends a Direct Request | `/api/v1/learning-requests` | POST | `CreateLearningRequest` **unchanged** (`teacherServiceId`, `title`, `description`, `preferredDeliveryAt`, `budget?`) — no price field | Bearer; role Student | `201 LearningRequestDto` + `listedPriceAtRequest: number`, `listedCurrencyAtRequest: string` | request row stores the offering's `Price` and `Currency` read server-side in the same query that validates eligibility |
| Open request detail / lists | `/api/v1/learning-requests/{id}`, `/mine`, `/assigned` | GET | — | Bearer; participant | `LearningRequestDto` + `listedPriceAtRequest: number \| null`, `listedCurrencyAtRequest: string \| null` (null for historical and Open Requests) | none |
| Teacher accepts at a price | `/api/v1/learning-requests/{id}/accept` | POST | `AcceptLearningRequest` **unchanged** (`finalPrice`, `currency`, `agreedDeliveryAt`, `revisionAllowance`, `deliveryHours?`) | `If-Match`, `Idempotency-Key` (unchanged) | `OrderDto` + the two fields | order created (unchanged); request snapshot untouched |
| Order detail | `/api/v1/orders/{id}` | GET | — | Bearer; participant | `OrderDto` + `listedPriceAtRequest: number \| null`, `listedCurrencyAtRequest: string \| null` (from the order's Learning Request) | none |
| Checkout and request detail find the order | `/api/v1/orders/mine?pageSize=…` (existing reads) | GET | — | Bearer | `PagedResult<OrderDto>` with the two fields | none |
| Pay | `/api/v1/payments/orders/{id}` (existing) | POST | unchanged | unchanged | unchanged; amount = `studentTotal` | unchanged |

**Smallest correct model change (Build guidance, reviewed at Gate 4):**
- **Domain** (`Tafseel.Domain/Orders/Orders.cs`, `LearningRequest`):
  - `public decimal? ListedPriceAtRequest { get; private set; }` and
    `public string? ListedCurrencyAtRequest { get; private set; }`;
  - one method `CaptureListedPrice(decimal price, string currency)`. It refuses when the sourcing mode is not Direct, when
    a snapshot already exists (`listed_price_immutable`), and when price or currency is invalid (same bounds as
    `TeacherService`: `0 < price ≤ 1,000,000`, 3-letter currency).
  - No other mutator. The constructors are unchanged, so existing Open Request and test constructions are untouched.
- **Service:** `OrderService.CreateRequestAsync` calls `request.CaptureListedPrice(row.service.Price, row.service.Currency)`
  next to `CaptureServiceIdentity`. This is the only production Direct Request creation path, so every new Direct Request
  has a snapshot.
- **Persistence:**
  - EF configuration: `ListedPriceAtRequest` precision (18,2), `ListedCurrencyAtRequest` max length 3;
  - one migration adding two **nullable** columns to `LearningRequests`, with **no data update/backfill**, and a check
    constraint that both are null or both are set;
  - reviewed on SQL Server and the provider-neutral (SQLite) suite.
- **Mapping:** `LearningRequestDto` and `OrderDto` gain two trailing optional members. `OrderService` already loads each
  order's Learning Request for `RequestTitle` (`OrderService.cs:551-553, 578-581`), so the same query projects the two
  fields.
- **Not snapshotted:** offering title, description, delivery hours, revisions, approach notes, or any history/audit table.
- **Contract gate:** DTO shapes updated in the contract inventory; `check-api-contract --strict` stays at 0 violations.

Error codes the UI must explain: none new for students (`listed_price_immutable` is an internal invariant and never
reachable from the UI). Existing: `teacher_service_not_found`, `service_price_out_of_policy`, `currency_mismatch` (teacher,
at acceptance).

## Acceptance criteria
- [ ] AC1 Every Direct Request created through the API stores the selected offering's price and currency at creation; the request body cannot supply or override it.
- [ ] AC2 Editing the Teacher Offering (before or after acceptance) never changes the stored snapshot.
- [ ] AC3 A second capture and a capture on an Open Request are refused by the domain.
- [ ] AC4 Historical Direct Requests keep a null snapshot (no backfill); responses return null; no comparison is shown.
- [ ] AC5 `LearningRequestDto` and `OrderDto` expose `listedPriceAtRequest`/`listedCurrencyAtRequest` to participants only; others get 404.
- [ ] AC6 With `listed ≠ agreed`, request detail (after acceptance), order detail (before payment) and checkout show the same four rows with the AR/EN labels above; with equal or null snapshot, no comparison row.
- [ ] AC7 Fee and total are computed from the agreed price (150 → fee 12 → total 162), never from 100 or 120; paying charges `studentTotal`.
- [ ] AC8 No forbidden wording; `«السعر المدرج»` / "Listed price" no longer labels the agreed price; labels are identical across the three surfaces.
- [ ] AC9 Open-request orders show no comparison; DEC-02 acceptance rules and all financial snapshots are otherwise unchanged (existing financial suites green).
- [ ] AC10 Migration adds nullable columns only, with the both-or-neither check, and no data update.

- Snapshotting any other offering field; offering version history; general audit history.
- Backfilling historical requests; Admin views of the snapshot; VAT wording (`DEC-08`).
- Changes to fee rules, order financial snapshots, payment or ledger code.
